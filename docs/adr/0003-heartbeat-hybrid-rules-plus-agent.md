# 心跳 = 规则硬过滤 + agent 软决策的混合架构

心跳周期（默认 30 分钟）到点时，先由**代码规则做硬过滤**（总状态为空闲、无 GTD 任务在跑即单飞、待办非休眠、执行器有余量——任一不满足则本轮静默、零 LLM 成本），通过后再起一个专门的**心跳 bot 会话做软决策**（daemon 把就绪待办摘要与各执行器余量喂进 prompt，它挑一条、写提议文案、预建议执行器、预估余量够不够），产出结构化（待办 id + 文案 + 建议），解析失败视为本轮沉默。理由：用户明确"以烧 token 为目的、不以省为目的"——自主性是核心，但把"决定本轮沉默"也交给 agent 意味着为沉默付钱；混合架构把 token 花在刀刃（挑活与措辞）上。心跳 bot 本身无权启动任何待办，确认门在其下游。

## Considered Options

- **纯规则引擎**（代码挑待办 + 模板文案）：被否——没有自主性，与功能的核心目的相悖。
- **openclaw 式纯 agent 心跳**（agent 全权决定提议或沉默）：被否——每跳必烧 token，包括"什么都不做"的判定；且规则条件（单飞、休眠）用代码表达远比 prompt 可靠。

## Consequences

- 硬过滤规则与心跳 bot 的软决策是两个独立层次，规则变更不需要动心跳 bot 的 prompt，反之亦然。
- 心跳 bot 的执行器/模型由用户配置，可故意指向有冗余的订阅执行器——心跳自身的消耗即是对冗余的利用，这是有意为之。
