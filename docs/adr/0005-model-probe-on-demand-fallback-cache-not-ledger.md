# 模型可用性以执行器原生配置为准：探测按需发起，兜底结果只做缓存

工作台的模型清单不建中央注册表、不建镜像账本，与 [ADR 0004](0004-mcp-native-config-single-source-of-truth.md) 对 MCP 的取舍同构：claude 读 `~/.claude/settings.json` 的 `ANTHROPIC_DEFAULT_*_MODEL`、codex 跑 `codex debug models`、dsh / grok / hermes / kimi / mcode 走 ACP `session/new` 的模型选单 —— 探测到的一切都以那次现场读取为准，不缓存、不预取。唯一额外持久化是 `<homeDir>/models-cache.json`：上一次**成功探测**结果的落盘副本，仅在探测失败时顶一下，删掉不影响任何真相源，下个冷启动重新探一遍即可。

启动不做自动预探测。冷启动只读盘上那份兜底（daemon 实测 db→listening 36ms），要最新的由用户点「探测模型」或「重新探测执行器」，两条路都汇到 `host.syncModels()`。

## Considered Options

- **启动时自动预探测**（否决）：每次启动并发拉起十来个 CLI 子进程去列清单（实测总耗时 28s，openclaw 一家就 28.5s），换来的"正确性"却是假的 —— fire-and-forget 的探测与界面的 `adapter.list` 赛跑，谁先谁后全看时序，预热没跑完时界面会把适配器内置的 3 条种子清单冻成快照，这正是"每次进去都是初始化态"的由来。
- **中央模型注册表 + 启动时投影**（否决）：与 0004 否决 cc-switch 投影模型是同一个理由 —— 引入第二真相源后，漂移收敛成为永久负担。模型可用性本来就随厂商上下线变动，比 MCP 配置更频繁，镜像必然长期跑偏。
- **什么都不缓存**（否决）：探测失败时只能退回各适配器的内置种子清单（claude 那 3 条 sonnet/opus/haiku），用户一眼就看出是"初始化状态"，而这正是要消灭的现象。
- **把缓存当权威、写进工作台数据库**（否决）：那就成了账本，与 0004 的「不建镜像账本」直接冲突。

## Consequences

- **探测结果的来源必须诚实**：只有真正从 CLI / 原生配置读到才报 `live`，失败一律 `static`。适配器已各自兜底一次，宿主层再兜一层（沿用盘上那份）并带上写盘时间，界面据此显示「· 来自上次探测 · X 前」。探不到就是探不到 —— 宁可告诉你多旧，也不假装新鲜；因此缓存**不设 TTL**，由用户决定什么时候重新探。
- **「本轮没探到」不等于「模型下线」**：只有 `source === "live"` 的那一轮才认定失效模型并从下拉框移除；探失败那轮沿用旧清单，失效判定一律不生效。否则一次网络抖动 / CLI 没启动就会让用户可选的模型凭空消失。
- **失效模型不静默替换**：用户正选着它、或定时任务配着它时，保持原值并标记不可用，交由他决定换不换。原先的静默回落会换成 daemon 列的第一个 —— codex 实测那是 $10/$50 每百万 token 的旗舰档 gpt-6-astra，等于什么都不选就按最贵的跑。
- **代价要说在明处**：首次安装（盘上尚无缓存）时启动看到的是内置种子清单，界面标「· 未刷新」，需点一次刷新才有真实清单。这是按需付费，不是把问题藏起来。
- 可见性判定的唯一入口是 `visibleModelsFor` 派生的 `isModelAvailable`，设置页 / 待办 / 定时任务 / 心跳横幅 / 顶栏共用。落点散开就会漏，漏一处等于用户能在定时任务里悄悄跑一个已下线的模型。
