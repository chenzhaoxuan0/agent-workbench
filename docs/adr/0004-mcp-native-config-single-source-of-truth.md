# MCP 管理以执行器原生配置文件为唯一真相源

工作台的 MCP 管理直接外科手术式读写各执行器自己的配置文件（`~/.claude.json` 的 `mcpServers`、`~/.codex/config.toml` 的 `[mcp_servers.*]`、`~/.gemini/settings.json`、`~/.config/opencode/opencode.json` 的 `mcp`、`~/.zcode/cli/config.json` 的 `mcp.servers`）；原生文件是唯一真相源，工作台不建运行时注入层，也不建镜像账本，唯一额外持久化是停用库（被移除条目的留档，恢复时写回）。

## Considered Options

- **中央注册表 + 会话启动时透传**（否决）：一次性 spawn 型执行器（zcode -p、codex）没有稳定的注入通道，最终仍要落盘写配置文件；且执行器原生 TUI 里看不到注册表中的配置。
- **真相源 + 投影模型**（cc-switch 现行方案，否决）：条目存工作台数据库，启停即向各执行器文件投影/撤投影。用户在实际使用 cc-switch 时遭遇过镜像与原生文件的冲突改写问题；引入第二真相源后，漂移收敛（导入合并、重同步）成为永久负担。决策：宁可每次实时读原生文件，也不维护镜像。

## Consequences

- 工作台打开管理页时实时读取原生文件，所见即真相；用户在原生 TUI 里的手改天然被尊重。
- 写入必须全程带乐观锁（读时记指纹、写前复查、不一致弹覆盖/重载/取消，复用 bot.json 的冲突范式）与首写字节级备份——没有账本可对账，安全护栏全部压在写入路径上。
- 跨执行器"复制"是一次性动作（读 A 家条目 → 格式转换 → 写 B 家），各家文件此后独立演化，不承诺一致。
- 同一原则已延伸到模型清单（执行器原生配置为准、不建镜像账本），但探测改按需发起、兜底结果另落一份缓存 —— 那是缓存不是账本，见 [ADR 0005](0005-model-probe-on-demand-fallback-cache-not-ledger.md)。本 ADR 上文「唯一额外持久化是停用库」说的是 MCP 这条线。
