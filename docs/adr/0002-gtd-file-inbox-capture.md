# GTD.md 收件箱模式作为待办捕获入口

待办的对话内捕获不依赖任何消息级协议交互，而是每个工作空间放一个 `<workdir>/GTD.md`（简单 checklist）作为**收件箱**：任何执行器的任何会话、以及用户本人用编辑器，都能追加条目；steward 每日统合（内置定时任务）把条目收录进待办清单（state.db，调度权威），语义去重后重写文件，把已收录条目移入"已收录"区并带上待办 id。理由：工作台接的 8 家 CLI 全是终端 TUI、消息选择交互无法统一实现，而"往自己工作空间的文件追加一行"对所有执行器零成本通用，且契合项目"文件即数据库"的既有哲学（AGENTS.md / bot.json 同理）。

## Considered Options

- **前端选中消息"存为待办"**：被否——PTY 画布里渲染的是各家 CLI 的 TUI，前端拿不到跨执行器统一的消息结构，无从选中。
- **自然语言识别（"把这个排进待办"）**：后置到 v1.1+——依赖各执行器工具调用能力，水平参差。

## Consequences

- `GTD.md` 的格式成为 8 家 CLI 与用户共同遵守的契约，变更需向后兼容；文件是收件箱不是权威，统合后调度只看待办清单，文件被手动清空不影响已收录条目。
- 统合有日级延迟，对 GTD 场景（长周期目标）可接受；防重复导入依赖 steward 的"已收录"标记回写。
